## NT-01 — Make valid meal input an explicit contract

**Status:** Ready · **Depends on:** existing app · **Size:** 45–90 minutes, adjustable.

**Problem:** The API currently accepts an empty meal name, an empty ingredient list, and negative ingredient weights. A client can bypass browser checks.

**Learn:** classes and instances, nested types, imports/packages, required fields, Pydantic constraints, Python dictionaries versus model instances.

**Files to create:** `app/schemas/__init__.py`, `app/schemas/meal.py`.
**File to edit:** `app/main.py`.

Move the two existing models into the schema module and import them into the app. Add a response model and declare it on the POST route. Keep the existing endpoints, UUID-string IDs, stored meal shape, and browser behavior.

| Model | Field | Contract for this ticket |
|---|---|---|
| IngredientCreate | name | Required string; at least one character. |
| IngredientCreate | grams | Required float; greater than zero. |
| MealCreate | name | Required string; at least one character. |
| MealCreate | ingredients | Required list of IngredientCreate; at least one element. |
| MealResponse | id | Required string generated by the server. |
| MealResponse | name | String. |
| MealResponse | ingredients | List of IngredientCreate. |

For this first slice, “nonempty” means length ≥ 1. Whitespace trimming, non-finite numbers, and unknown input fields are a deliberate follow-up in NT-04. Retain normal Pydantic numeric coercion for now; do not silently switch the whole API to strict types.

**Acceptance checks**

- [ ] A valid payload still creates and retrieves a meal with all ingredients.
- [ ] Instantiating IngredientCreate with grams 0 or -1 fails validation.
- [ ] Empty meal name, empty ingredient name, and empty ingredients fail validation.
- [ ] All fields shown as required really are required.
- [ ] POST still returns 201 and a body with exactly `id`, `name`, and `ingredients`.
- [ ] The original 3 application tests still pass.

Use this input to see the valid result:

```json
{"name":"Oatmeal","ingredients":[{"name":"Oats","grams":50}]}
```

The response and stored record both contain a generated string `id`, the name, and the ingredient list. Never assert a particular random ID; capture it from the response.

**First action now:** create `app/schemas/meal.py`, move the models, and implement the three model contracts above. Run the existing application tests, then move directly to NT-02.

**Explain at review:** What is the difference between `meal.ingredients[0]` and `meal.model_dump()["ingredients"][0]`? Why can a Python type annotation alone be insufficient to enforce a positive weight?

**Hints, only as needed:** look up `BaseModel`, `Field`, `min_length`, `gt`, `model_dump`, and the route's `response_model` parameter. Pydantic provides field constraints; FastAPI uses request models for body validation. [Pydantic fields](https://pydantic.dev/docs/validation/latest/concepts/fields/), [FastAPI request bodies](https://fastapi.tiangolo.com/tutorial/body/).

## NT-02 — Prove schema behavior with pytest

**Status:** Backlog · **Depends on:** NT-01 · **Size:** 45–90 minutes.

**Create:** `tests/test_meal_schemas.py`.

Start with one ordinary successful test and one `pytest.raises(ValidationError)` test. Run each. Then parametrize related invalid cases. Construct models directly here; no TestClient is needed.

**Acceptance checks**

- [ ] Valid nested input produces an IngredientCreate instance with the expected name and grams.
- [ ] `model_dump()` produces the expected nested dictionary/list shape.
- [ ] Parametrized zero and negative grams raise ValidationError.
- [ ] Empty meal name, empty ingredient name, and empty ingredient list each raise ValidationError.
- [ ] Missing required name, grams, and ingredients are covered in their respective models.
- [ ] A small positive weight is accepted: the lower boundary is exclusive, not rounded up to 1.
- [ ] Remove a constraint briefly, observe its test fail, then restore the constraint and see the test pass.

Suggested names include `test_valid_meal_builds_nested_ingredients` and `test_ingredient_rejects_nonpositive_grams`. Assert observable behavior, not the exact wording of a library's entire error message.

**Commands from the repository root**

```bash
uv run python -m pytest tests/test_meal_schemas.py -q
uv run python -m pytest tests -q
```

**Explain at review:** Why does a test expecting an exception pass when that exception occurs? How many cases does your parametrized test execute? A parametrize decorator runs a test with multiple sets of arguments. [pytest parametrization](https://docs.pytest.org/en/stable/how-to/parametrize.html).

## NT-03 — Prove the HTTP boundary and isolate storage

**Status:** Backlog · **Depends on:** NT-02 · **Size:** 1–2 sessions.

**Create:** `tests/conftest.py`. **Extend:** `tests/test_meals.py`.

Use a client fixture that isolates `meals_content` for each API test. Preserve the current seeded-data convention: take a deep snapshot before the test and restore it in teardown. Mutate the existing dictionary with clear/update rather than rebinding it, so imports still refer to the same object. Use a fresh payload per test. The later repository ticket will replace global-state setup with dependency injection.

**Acceptance checks**

- [ ] Valid POST gives 201, has exactly the response fields, and returns a nonempty string ID.
- [ ] GET of that ID returns the exact saved record; listing includes it.
- [ ] Two successful requests produce distinct IDs and store both records.
- [ ] Zero/negative grams, missing name, empty names, and empty ingredients produce 422.
- [ ] For invalid requests, compare storage with a deep copy from before the request; it is unchanged. Do not expect empty storage when there are seeded meals.
- [ ] Missing meal retrieval still returns 404 and the existing error body.
- [ ] Run the new tests alone, then together with the existing tests in a different file order; results agree.
- [ ] Fixture teardown restores storage even when a test assertion fails.

**Explain at review:** Direct schema construction raises a Python exception; request validation is handled at the HTTP boundary. Trace where invalid input stops. Explain what `yield` and `with TestClient(app)` do in your fixture. TestClient exercises the app without requiring a separately running server. [FastAPI testing](https://fastapi.tiangolo.com/tutorial/testing/).

## NT-04 — Harden the edge cases after the first working slice

**Status:** Backlog · **Depends on:** NT-03 · **Size:** 1 session.

Choose and implement this explicit contract: trim names, reject names that become blank, require finite positive grams, and reject unknown request fields (including a client-supplied `id`). Keep numeric-string coercion for weights and document it. The response schema is a separate output contract; server-generated `id` is allowed there.

**Acceptance checks:** whitespace-only names fail; padded names are stored trimmed; direct model construction rejects NaN and positive/negative infinity; unknown fields fail through both model and API validation; valid browser-shaped JSON still works. For HTTP tests, use valid JSON payloads—non-finite values are not standard JSON numbers. Cover numeric-string coercion intentionally instead of depending on an unexamined default.

**Explain at review:** Which decisions describe product input policy? Which are library defaults? How does validation differ from sanitization and from database constraints?
